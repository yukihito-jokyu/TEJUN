# 画面Issueプランナー

入力情報をそのままIssueへ分割せず、リポジトリの既存画面・規約との接続を先に確認する。ユーザーが設計判断を確認できるよう、下書き提出とGitHub登録は明確に分ける。

## 最初の対話

渡された要件、画面、コード、URLを読み、対象画面と実現したい操作を短く要約する。重要な情報が不足している場合だけ、次のうち必要な1〜3問を尋ねる。

1. 対象とする画面と、その画面で利用者が完了したい操作は何か。
2. 参照すべき要件、画面、既存画面、コード、Figma URLはどれか。
3. Issueを登録するGitHubリポジトリはどれか。Gitリモートから判別できない場合は `owner/repository` またはURLを確認する。

判断に必要な情報が未確定なら推測でIssue案を作らない。何を決める必要があるか、選択肢と影響を短く示してユーザーへ確認する。

## リポジトリ調査

調査前に [repository-audit.md](references/repository-audit.md) を読む。各判断は既存コードまたは規約への参照を残し、根拠なしに新しいドメイン名、ディレクトリ、テストコマンド、ラベルを作らない。

実装が存在しない、または技術スタックが確認できない場合は、まず「詳細設計で既決の業務上のまとまり」と「実装選択がないと決められない事項」を分ける。ドメイン境界を整備対象にするのは、API所有、モジュール配置、トランザクション境界、認可境界、実ディレクトリのいずれかを追加で決定し、後続Issueへ反映する場合だけである。

技術スタックが未決なら、構造や検証を推測で確定しない。原則として、`技術スタック → 層ごとの実装構造 → 層ごとの検証 → 横断検証 → 画面実装Issue` の依存順で調査・下書きする。

調査対象は次である。

- 他画面との業務概念、データ、API、UIの親和性と所有ドメイン
- フロントエンド、バックエンド、永続化、横断のどの層が各関心を所有するか
- 技術スタックと、層ごとの実装構造（ディレクトリ配置とファイル責務）
- unit、API契約・結合、画面結合、E2E、アクセシビリティ、静的解析の規約と実行コマンド
- GitHub Issueの種別、ラベル名、付与条件、管理者、既存ラベル

調査結果を、根拠・確定事項・ユーザーと決める事項・不足している規約に分けて提示する。

## 整備ゲート

技術スタック、実装構造、検証方法、Issue種別・ラベル規約のいずれかを決められない場合は、画面実装の分解へ進まない。詳細設計で既決の業務上のまとまりだけを理由に、ドメイン境界の整備Issueを作ってはいけない。

不足した独立した決定ごとに、`type: maintenance` の整備Issue案を1件だけ作る。複数層を扱う関心は原則として層ごとに分け、横断Issueにする場合は単一層へ帰属できない理由を記載する。整備Issueには、対象の規約、対象層、依存する決定、実ディレクトリへの影響、決定する内容、保存先、受け入れ基準、完了後に再調査することを記載する。

### 構造統合の判定

同じ層でディレクトリ配置とファイル責務が相互依存し、片方だけでは安定した受け入れ基準を作れない場合は、`<層>の実装構造` として1 Issueに統合する。配置と責務が独立して変更・レビューできる根拠がある場合だけ分離し、その根拠をIssueへ記載する。

このモードでは、同じ出力に画面実装、フロントエンド、バックエンド、APIのIssue案を含めない。整備Issueの承認・実施・再調査を終えた後に、あらためて画面実装の分解を開始する。

## 画面Issueを設計する

整備ゲートを通過した場合、対象画面ごとに1つの `feature` Issue案を作る。フロントエンド、バックエンド、API、テストを子Issueへ分けず、その1Issueに含める。親Issue・子Issue・レイヤー別ラベルは作らない。

各画面について、次の順にユーザーと決める。

1. 既存画面との共通性を比較し、既存ドメインへ置くか新規ドメインにするかと理由を確認する。
2. 既存構造に沿って、画面固有、共有UI、状態処理、APIクライアント、HTTP、業務処理、永続化の配置とファイル境界を確認する。
3. 追加・変更するAPIごとに、利用者、画面、クライアント、HTTP、業務処理、永続化、正常・異常分岐をMermaidシーケンス図で確認する。APIを追加・変更しない画面では、その理由をIssueに記録する。
4. シーケンス図の分岐と画面操作を起点に、テスト観点、項目、テスト種別、完了条件を確認する。

Issue本文は [issue-draft-template.md](references/issue-draft-template.md) に従う。テストは少なくとも、共有ドメイン、API、画面状態、E2E、アクセシビリティ、既存画面の回帰について、該当・非該当と理由を明記する。該当するものは具体的な入力、期待結果、実行コマンドを記載する。

## 種別とラベル

リポジトリの規約を優先する。規約がない、ラベル名・付与条件・管理者が決まっていない、または必要なラベルがGitHubに存在しない場合は、Issue分類またはラベル設定に関する整備Issueを作り、画面Issueを作らない。

規約が整っている場合は、次を守る。

- `type` は各Issueに1つだけ。画面実装は `feature`、リポジトリ整備は `maintenance`、不具合修正は `bug` とする。
- 画面Issueには主要な業務概念を表す `domain:<name>` を1つ、画面を表す `screen:<name>` を1つ付ける。
- `frontend` と `backend` のレイヤーラベルは付けない。両方の実装範囲をIssue本文へ記載する。
- 整備Issueのラベルは、既存規約がある場合だけ付ける。分類規約自体が未整備ならラベルなしの下書きにする。

## 下書きと検証

ユーザーが保存先を指定しない場合、現在のプロジェクトに `screen-issue-planning/` を作る。過去runを変更せず、`run-NNN` を新設する。

```text
screen-issue-planning/
└── runs/
    └── run-NNN/
        ├── input-record.md
        ├── repository-assessment.md
        ├── issue-plan.json
        ├── validation.json
        └── simulation/
            ├── issue-drafts.md
            ├── issue-manifest.json
            └── simulated-registration.json
```

`issue-plan.json`には、モード、調査で不足した関心ごと、Issueごとの種別・ラベル・画面または整備関心・本文・API・テスト観点を記録する。新規runは `schema_version: 2` とし、整備Issueには、`layer`、`depends_on`、`physical_impact` を必ず記録する。`cross-layer` には `cross_layer_reason`、配置と責務を統合した実装構造には `merge_rationale`、両者を分離した場合には `separation_rationale` を記録する。既存の `schema_version: 1` のrunは読み取り・検証だけを互換対象とし、編集しない。本文を完成させてから、次を実行する。`<skill-dir>` はこのSKILL.mdがあるディレクトリである。

```bash
python3 <skill-dir>/scripts/validate_issue_drafts.py \
  --input <run>/issue-plan.json \
  --output <run>/validation.json

python3 <skill-dir>/scripts/simulate_github_registration.py \
  --input <run>/issue-plan.json \
  --validation <run>/validation.json \
  --output-dir <run>/simulation
```

検証が失敗したら生成済みrunを編集しない。根拠、対話記録、またはIssue案を新しいrunで修正して再生成する。`simulation/`の模擬登録結果はGitHubへ送信しない。ユーザーへIssue案、調査結果、検証結果、未解決事項を提示して確認を得る。

## GitHubへの登録

ユーザーが明示的に「登録してよい」と承認するまで、GitHubへの書き込みを行わない。下書き確認の承認と登録承認は別である。

登録承認後は、対象リポジトリと既存ラベルを確認する。ラベルが不足・不一致なら登録を停止し、分類またはラベル設定の整備Issueを先に提案する。承認済みの本文・タイトル・ラベルと一致するIssueだけを、画面ごとに1件ずつ登録する。

登録が1件成功するたびにIssue URLと下書きIDを記録する。途中で失敗したら直ちに停止し、登録済みIssueを再作成しない。未登録分、失敗理由、登録済みURLをユーザーへ報告し、再開の承認を得る。GitHub上の既存Issueを変更・削除しない。

完了時は、Issue案の保存先、作成したIssue URL、実際に付与した種別・ラベル、実行した検証、未解決事項を短く渡す。
