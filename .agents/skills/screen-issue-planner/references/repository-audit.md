# リポジトリ調査の手引き

## 調査の順序

1. 要件、画面HTML、Figma、既存コードから、対象画面と隣接画面を特定する。
2. 詳細設計から既決の業務上のまとまりを抽出し、追加のドメイン判断が実装へ影響するかを確認する。
3. プロジェクトの指示、README、ADR、設計文書、依存定義、ルーティング、機能ディレクトリ、テスト設定、CIを読む。
4. 技術スタック、フロントエンド、バックエンド、永続化、横断、運用の各層について、未決の決定と依存順を調べる。
5. 各画面が扱う業務概念、型、API、共有UI、利用者操作を比較する。
6. Issueテンプレート、過去Issue、GitHubラベルを確認できる場合は、種別とラベルの実運用を調べる。

## 判定記録

`repository-assessment.md` には各項目について、結論、根拠のファイルまたはURL、確信度、未決なら質問を書く。

| 項目 | 決めること | 規約が不足している兆候 |
| --- | --- | --- |
| ドメイン境界 | どの業務概念が画面とAPIを所有するか | 同じデータや規則が画面ごとに別名・別場所へ複製されている |
| ディレクトリ | 画面固有、共有、サーバー側の置き場所 | 新規ファイルの配置先を複数案から選べない |
| ファイル分割 | UI、状態、API、業務、永続化の責務 | 既存ファイルに複数責務が混在し、切り出し基準がない |
| テスト | 種別、fixture、標準コマンド、CI必須条件 | テストの配置・実行・責務を既存例から判断できない |
| Issue分類 | type、ラベル名、必須・任意、管理者 | ラベルを推測する必要がある、またはGitHub上に必要なラベルがない |

## 層と依存順の判定

整備候補ごとに、`frontend`、`backend`、`persistence`、`cross-layer`、`operations` のうち主な所有層を1つ記録する。複数層へまたがる候補は、単一層へ帰属できない理由がある場合だけ `cross-layer` にする。

実装が存在しない、または技術スタックが未決の場合は、技術スタックを最初の整備対象にする。後続の構造・検証Issueには、その決定を `depends_on` として記録する。

同一層のディレクトリ配置とファイル責務は、互いの決定を変更し得るなら1つの実装構造Issueに統合する。分離する場合は、別々に変更・レビューできる根拠を `separation_rationale` として残す。

## 整備ゲートの出力

不足を見つけたら、各行を独立した整備関心として扱う。たとえば「ディレクトリ」と「ファイル分割」は別Issueである。整備Issue案には、対象外の画面実装・API実装を混ぜない。

確信度が低いだけで整備Issueを作らない。既存コード・文書を確認しても一意に判断できず、ユーザーとの議論でも規約を決める必要がある場合に整備Issueとする。
